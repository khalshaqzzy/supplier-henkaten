# ADR 0057: High-Severity Security Hardening, Realtime SSE Isolation and Least-Privilege Runtime Database Role

- Status: Accepted
- Date: 2026-11-26

## Context

A comprehensive security review of the application, realtime streaming, audit boundaries, deployment scripts, and hosted container topology identified seven high-severity security weaknesses requiring immediate remediation without disrupting live deployments or rollback continuity:

1. **TMMIN Internal Part Number leakage (H-01):** Shared Henkaten list and detail handlers exposed `parts[].internalNumber` and searched `internalPartNumberSnapshot` unconditionally on TMMIN endpoints, and `HENKATEN_EXPORT_REQUESTED` audit rows persisted raw `filters.part` strings readable by TMMIN roles.
2. **Cross-realm audit disclosure to Supplier roles (H-02):** `supplierAudit` and `supplierDashboard.recentActivity` filtered only by `supplierId`, allowing `SUPPLIER_ADMIN` and `QC` accounts to read TMMIN-authored audit events (including `HENKATEN_DELETED` reasons, magic-link impersonation events, TMMIN read logs, `EXTERNAL_CLIENT` records, and TMMIN-only `NOTIFICATION_GENERATED` system rows) and resolve TMMIN user display names.
3. **Supplier SSE event allowlist and wire-schema alignment (H-03):** `RealtimeEventPump` and `RealtimeService` forwarded non-supplier outbox events (`PCR_REVIEW_REQUIRED`, `EXTERNAL_*`, `MEMBER_PHOTO_CLEANUP_REQUESTED`, and external PCR aggregates) to supplier streams, omitted `payload.lineId` on multiple line-scoped producers, exposed TMMIN `HenkatenDeletionCommand` IDs, and serialized `lineId` onto wire messages rejected by the strict client `realtimeInvalidationSchema`.
4. **Unbounded `dashboardTrend` bucket allocation (H-04):** `tmminDashboardQuerySchema` accepted arbitrary date spans and `dashboardTrend()` iterated across every interval synchronously (while taking `records.at(-1)` on unordered queries), enabling CPU/OOM exhaustion.
5. **Unbounded concurrent SSE streams and DB query amplification (H-05):** `GET /api/v1/supplier/realtime` imposed no concurrent stream limits, held open heartbeat streams for unknown `lineId` parameters, and executed 4–8 SQL queries per emitted message (including up to 500 replayed events per reconnect) against a bounded PostgreSQL pool.
6. **Shell evaluation during `.env` validation and loading (H-06):** `deploy/scripts/lib.sh:load_runtime_env()` invoked Bash `source` on unvalidated `.env` files before validation, and `render-runtime-env.sh` accepted unvalidated `PRODUCTION_*_DOMAIN` hostnames.
7. **Superuser runtime PostgreSQL connection (H-07):** The internet-facing `api` container shared the `POSTGRES_USER` bootstrap superuser role with `migrate`, permitting a compromised API runtime to disable audit-immutability triggers or run privileged SQL.

An eighth organizational item—separating staging/production SSH keys and adding a manual production GitHub Environment approval gate (H-08)—is explicitly deferred to a separate infrastructure governance task.

## Decision

1. **Realm-scoped Internal Part Number enforcement with staged Release 1 wire compatibility (H-01):**
   - `HenkatenService.list()` and `.get()` derive `includeInternal = principal?.realm === 'SUPPLIER'` (fail-closed `false` for TMMIN), blocking both `henkatenPartSearch` on internal numbers and output disclosure while preserving all supplier read, write, and export (`presentHenkatenParts(row, supplierView)`) paths.
   - TMMIN hosted Henkaten list/detail responses emit `internalNumber: null` in Release 1 alongside dedicated `tmminHenkatenPartSchema` (`internalNumber: z.null().optional()`), `tmminHostedHenkatenPageSchema`, and `tmminHostedHenkatenDetailSchema` contracts. Keeping the key as `null` in Release 1 prevents transient strict-Zod parse errors on already-open `tmmin-web` tabs during forward rollout; conversely, `packages/api-client/src/tmmin.ts` normalizes any legacy string `internalNumber` from a rolled-back pre-H-01 API to `null` at the client parsing boundary without exposing it to UI state, while keeping server and OpenAPI schemas strict. Omitting the key entirely can proceed in a follow-up contract release once old bundles cycle out.
   - `HenkatenExportService.create()` omits raw `filters.part` from `AuditEvent.changeSummary` and records `partFiltered: Boolean(part)`. `redactAuditSummary()` recursively sanitizes nested objects/arrays (failing closed at recursion depth 8 with `'[REDACTED]'`), strips historical `HENKATEN_EXPORT_REQUESTED` `filters.part` values for TMMIN reads, and replaces `tmminOperatorId`/`operatorUserId` with `impersonated: true` on Supplier audit reads. Impersonated TMMIN support sessions operating inside the `SUPPLIER` realm intentionally retain Supplier Admin view semantics per existing support-access rules.

2. **Fail-closed Supplier audit and dashboard isolation (H-02):**
   - Both `supplierAudit()` and `supplierDashboard()` apply a shared `supplierVisibleAuditWhere(supplierId)` predicate before pagination/`take: 20`: `sourceMode` must be null or `HOSTED`; `USER` events require a supplier role and matching `actorSupplierId` (when populated); `SYSTEM` events require an explicit allowlist of supplier-visible actions (`SHIFT_TIMES_ROTATED`, `HENKATEN_CANCELLED`, `HENKATEN_OPENED`, `USER_CREATED`, `SHIFT_ENDED`, `LINE_SHIFT_CONFLICT_CLEARED`) and non-external/non-TMMIN resource types; and TMMIN/External action prefixes and names are excluded as defense in depth.
   - `supplierDashboard()` restricts actor display-name lookup to `realm: 'SUPPLIER'` and `supplierId: scope.supplierId`.

3. **Allowlisted Supplier SSE, server-side line routing and monotonic replay handoff (H-03 & H-05):**
   - `RealtimeEventPump.poll()`, `RealtimeService.replay()`, and `RealtimeService.inScope()` enforce a shared allowlist (`SUPPLIER_SSE_LINE_SCOPED_EVENTS` and `SUPPLIER_SSE_TENANT_WIDE_EVENTS`) and block `ExternalHenkatenProjection` and `ExternalApiClient` aggregates.
   - Line-scoped outbox producers (`WARNING_OPENED`, `HENKATEN_APPROVAL_RECORDED`, `OperationalFinalizationService.closeTerminalEffects` across withdraw/decide/shift-end, `ManMovementService`, and hosted `PcrService`) populate `payload.lineId` (and `sourceLineId` for cross-line `MP_MOVED`).
   - Routing metadata (`lineId`/`sourceLineId`) stays strictly server-side and is omitted from wire `StreamMessage.data` so events match the strict `realtimeInvalidationSchema`. `HENKATEN_DATA_DELETED` rewrites wire metadata to `aggregateType: 'Supplier'` and `aggregateId: supplierId`.
   - `RealtimeEventPump.poll()` uses a bounded 10-second late-commit lookback backed by a strictly monotonic `confirmedCursor`, explicit leading `occurredAt >= cursor.occurredAt` range bounds alongside `(occurredAt, id)` pagination, and an additive leading index (`OutboxEvent_occurredAt_id_idx` via migration `20261126002800_outbox_realtime_poll_index`): after 10 s of silence, `poll()` completes one final overlapping lookback sweep (delivering any late commit that landed just before expiry) before confirming `confirmedCursor` and converging subsequent idle polls to bounded strict-cursor index seeks; multi-page polling stops immediately when `beforeApplicationShutdown()` sets `stopping = true`; and dense bursts exceeding `MAX_POLL_EVENTS = 2_000` or `MAX_PUBLISHED_IDS = 5_000` advance `confirmedCursor`, emit an immediate `resyncs()` signal, and schedule one bounded follow-up `resyncs()` after 10 s to reconcile any transaction that committed across the overflow boundary.
   - `replay()` validates `Last-Event-ID` as UUID before querying, runs under a separate replay DB concurrency budget sized against `DB_POOL_MAX` (`globalCap = max(1, floor(dbPoolMax / 4))` — 5 for `DB_POOL_MAX=20`, reserving ≥75% of the pool for API traffic; `userCap <= 2`) held until the SQL work settles (never released early on slot eviction, immediately falling back to `resync` without querying DB when saturated), filters suppressed/non-allowlisted/out-of-scope cursors and replay rows before counting `REPLAY_LIMIT`, uses explicit leading `occurredAt >= scanCursor.occurredAt` bounds, stops paginating immediately if the client closes mid-replay, and buffers live pump events before replay starts using ID deduplication (`recordSeen`), tolerating late-committed transactions within the bounded 10-second lookback window. `MASTER_DATA_REMOVED` remains deliverable to unfiltered supplier-wide board streams even after a deleted line is tombstoned, while line-filtered streams for that deleted line close cleanly.
   - `SupplierReadModelController.realtimeEvents()` rejects non-GET methods (`405 Allow: GET`), validates `lineId` (`404`), bounds concurrent in-flight admissions, and acquires per-process connection slots (`SSE_MAX_PER_SESSION=6`, `SSE_MAX_PER_USER=12`, `SSE_MAX_PER_SUPPLIER=60`, `SSE_MAX_GLOBAL=300`) **before** SSE headers commit via direct Express streaming (`handleHttpStream` + `formatSseFrame`, omitting `id:` on heartbeats/resyncs to preserve `Last-Event-ID`). Slot release is bound idempotently to `response.once('close', release)` and RxJS teardown (never `request.once('close')`, which fires prematurely on Node 22 when `express.json()` drains zero-length bodies). Per-session overflow evicts the oldest stream with a 30–60 s jittered `retry` hint and a bounded (`MAX_EVICTING_SOCKETS = 16`) 2 s unref'd socket-destroy grace budget (destroying stalled or over-budget evicted sockets immediately) before checking user/supplier/global `429` limits; `packages/api-client/src/realtime.ts` adds bounded exponential-backoff reconnect when `EventSource` enters `CLOSED`, and `BoardPage.tsx` uses `scopedKeyPrefix()` (omitting the trailing `params` slot) to invalidate all four parameterized query families (`assignment-board`, `assignment-board-layout`, `notification-count`, `dashboard`) on `onInvalidate`, `onResync`, and `onReconnect`. Session and line-scope checks run once per replay batch, on a chained non-overlapping 15 s cache-bypassing heartbeat (coalesced across tabs of the same session via `sessionBypassInFlight`), and through a monotonic-epoch coalesced micro-cache (`SSE_REVALIDATION_CACHE_MS=2000`) on live bursts with bounded mid-flight epoch retries in `loadAllowedLines()` and single tenant-level cache invalidation per event; pending live events are bounded (256 items / 512 KiB writer hard cap calling `response.destroy()`) and defer a single `CURSOR_UNAVAILABLE` resync until `drain`.

4. **Inclusive UTC bucket ceilings on `dashboardTrend` (H-04):**
   - Shared UTC bucket helpers (`packages/contracts/src/tmmin.ts`) normalize years cleanly with `setUTCFullYear` and enforce inclusive ceilings with timezone slack (`DAY=370`, `WEEK=265`, `MONTH=122`) on two-sided and single-ended queries in `tmminDashboardQuerySchema`, rejecting raw `from > to`, pre-1970, and post-2100 timestamps.
   - `dashboardTrend()` computes the true `max(occurredAt)` on unordered records, returns `[]` on raw inverted ranges, clamps wide derived spans forward to the most recent `N` buckets, and enforces a hard loop ceiling.

5. **Non-evaluating closed-allowlist `.env` loader and strict FQDN validation (H-06):**
   - `deploy/scripts/lib.sh:load_runtime_env()` replaces `source` with a two-pass non-evaluating Bash parser backed by a closed allowlist of known runtime environment keys (rejecting CRLF, duplicates, unknown keys such as `PATH`/`BASH_ENV`, and shell metacharacters before resetting prior allowlisted variables and assigning via `printf -v` + `export`).
   - Strict RFC-1123 FQDN validation (`validate_fqdn`) applies in both `render-runtime-env.sh` and `validate-runtime-env.sh`.
   - Deploy/rollback state hardening (image pins, legacy baseline backfill, shared strict rollback driver, fail-closed recovery and interruption handling) is specified in Decision 7.
   - `POSTGRES_APP_PASSWORD` length validation (`32..128` URL-safe characters) is enforced identically across `render-runtime-env.sh`, `validate-runtime-env.sh`, and `apps/api/src/cli/migrate.ts`.

6. **Staged zero-touch least-privilege PostgreSQL runtime role (H-07):**
   - `apps/api/src/cli/migrate.ts` provides a distroless Node entrypoint invoked by the existing `migrate` Compose service (preserving the 7-service topology). After `prisma migrate deploy`, it idempotently creates or reconciles `POSTGRES_APP_USER` (`LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS`) using a Node-computed SCRAM-SHA-256 verifier passed via `set_config` so plaintext passwords never enter SQL statements or PostgreSQL logs.
   - Effective privileges are verified and reconciled on every deploy: zero owned objects and zero role memberships; `REVOKE` on `PUBLIC` and table-level privileges before granting `SELECT, INSERT, UPDATE, DELETE` on mutable app tables, `SELECT` only on `_prisma_migrations` (for `/ready`), `SELECT, INSERT, UPDATE ("hiddenAt")` on `AuditEvent` and `ExternalIngestionEvent`, no `DELETE`/`TRUNCATE` on `Henkaten` and `ExternalHenkatenProjection`, and `SELECT, INSERT` only on immutable append-only ledger tables, followed by a live `pg.Client` non-superuser login check.
   - `docker-compose.remote.yml` passes only `POSTGRES_APP_USER`/`POSTGRES_APP_PASSWORD` into `api` and `bootstrap-admin` (never `POSTGRES_PASSWORD`).
   - **Staged zero-touch provisioning:** `deploy-reusable.yml` forwards optional `POSTGRES_APP_USER` and `POSTGRES_APP_PASSWORD` secrets; when `POSTGRES_APP_PASSWORD` is unset, `render-runtime-env.sh` derives a one-way 64-hex `HMAC-SHA256` credential via `python3`/`node` reading `POSTGRES_PASSWORD` from the environment (never CLI arguments) so existing staging and production environments upgrade seamlessly without manual pre-steps, while allowing independent secret adoption at any time.

7. **Pinned, fail-closed deploy and rollback state machine (H-06 deployment hardening):**
   - **Image pins and containerd retention tags:** every activation records the five running image IDs (`postgres`, `api`, `supplier-web`, `tmmin-web`, `caddy`, strictly validated as `^sha256:[0-9a-f]{64}$`) in `releases/<sha>/.activated-images` via `write_activated_images()` (mktemp temp/backup files, exact-destination renames, rejection of non-regular or symlinked `.activated-images`/`.rollback-unsafe`, backup restore on any post-rename error, and mandatory verification that all five runtime tags resolve to the recorded IDs on non-backfill activations). Under Docker Engine's containerd image store, moving the sole tag on an image deletes the previous unreferenced image record immediately instead of leaving a classic dangling image; every pinned image ID is therefore retained by a content-addressed tag (`supplier-henkaten-pin-<APP_ENV>:<service>-<digest>`, validated by `validate_image_id()` and `pin_image_id()`). Before `docker compose build`, `remote-deploy.sh` ensures retention tags exist for the previous release, any already-activated target release being redeployed cross-SHA, and opportunistically for other retained releases; `ensure_manifest_pins()` distinguishes confirmed-missing images (`No such image` / `not found`, exit `2`, while still pinning every locally present image) from indeterminate/operational Docker errors (exit `1`) and malformed manifests (exit `3`), aborting before `docker compose build` on any operational error so transient daemon failures never overwrite an unpinned healthy baseline. Immediately after build, all five built IDs are captured and pinned into a staged candidate manifest before opening the service mutation window. `remote-deploy.sh` passes `BUILDX_NO_DEFAULT_ATTESTATIONS=1` to `docker compose build` so unchanged rebuilds (notably PostgreSQL) retain stable image IDs instead of churning OCI provenance manifest-list digests (Compose's `build.provenance: false` did not disable Buildx default attestations on current Compose versions); correctness does not depend on this optimization. Pin verification/staging runs inside `candidate_deploy()`, so failure routes through fail-closed recovery instead of advancing `current_release`; new releases commit `.activated-images` before pointers, while already-activated releases publish pointers before swapping `.activated-images` (with backup restore on error). `restore_pinned_images_file()` requires all five expected entries, separates confirmed policy violations (malformed manifest or confirmed-missing local ID, exit `2`) from retryable operational Docker failures (daemon/tag/verify errors, exit `1`), verifies every pinned ID exists locally before retagging, re-verifies each restored runtime tag, and re-asserts its retention tag.
   - **Exact-image reconciliation and one-off operations:** `ensure_service_runs_image()` reconciles each service individually (`postgres` first, configured with `stop_grace_period: 60s` for clean PostgreSQL checkpoints, then `api`, `supplier-web`, `tmmin-web`, and `caddy --remove-orphans`). Container ID queries run through `compose_ps_ids()`, capturing stdout separately from stderr so Compose warnings never contaminate container-ID parsing. Before starting a service, `ensure_service_runs_image()` inspects any existing container (including stopped containers via `compose ps --all -q`) and runs `compose up -d --no-deps --no-build --pull never`, adding `--force-recreate` whenever `Config.Image`, `.Image`, or local image inspectability diverges from the expected target, followed by health wait and post-reconciliation verification. One-off `migrate`, `bootstrap-admin`, and rollback `--provision-role-only` commands pass `--no-deps --pull never` and verify that the `api` tag resolves to the expected image ID immediately before each invocation.
   - **Retention and narrow pin pruning:** post-activation retention deduplicates same-SHA releases, prioritizes locally verified rollback-capable activated releases (`release_is_verified_rollback_target()`, verifying strict manifest syntax and local image presence before evicting older verified releases) within the 5-release budget, removes stale application tags with `docker image rm --no-prune`, and invokes `prune_unreferenced_pin_tags()` to remove only `supplier-henkaten-pin-<APP_ENV>:*` tags unreferenced by kept manifests (skipping pruning entirely if any kept `.activated-images` manifest fails strict validation).
   - **Legacy baseline backfill:** before `docker compose build`, an unpinned previous release (the first hardened deploy over `db60208`) gets `.activated-images` backfilled from its running containers only if each service has exactly one running container whose `Config.Image` equals that release's exact image reference and whose nanosecond `.Created` is strictly earlier than the `current_release` mtime (empty/unparseable timestamps fail closed) and whose `.Image` is inspectable locally. Otherwise the release is marked `.rollback-unsafe` before build, and the deploy aborts if neither pins nor the marker can be persisted. The timestamp check is a legacy-only wall-clock heuristic (it assumes `current_release` is not touched or restored manually and the clock does not step backwards). **Accepted residual risk:** if a legacy deploy rebuilt the shared PostgreSQL tag and a completed legacy rollback then restarted PostgreSQL from it for an older application SHA, the backfill pins that actually-running combination; no independent PostgreSQL record exists for legacy releases, and it is exactly what was live and passed smoke. `.agent/deploymentGuide.md` §9.5 holds the optional read-only production check. The backfill is gated by `release_is_hardened()` (shared by deploy and rollback): a release whose stored `.runtime.env` carries `POSTGRES_APP_USER` or whose tree ships `apps/api/src/cli/migrate.ts` is never backfilled, because hardened releases record pins at activation and a missing manifest therefore indicates lost evidence rather than a legacy baseline. For such a previous release, a same-SHA redeploy is refused before build and a cross-SHA deploy marks it `.rollback-unsafe` before build, so it can no longer be a rollback target.
   - **Snapshots and same-SHA redeploys:** the pre-build snapshot uses the previous release's own PostgreSQL reference and its pinned IDs. Same-SHA active redeploys fail fast before building when pins are missing or unavailable, and never mutate an activated release's immutable `.runtime.env`.
   - **Shared hardened driver:** `install_hardened_rollback_driver()` quarantines any pre-versioning real `rollback-driver` directory as `rollback-driver.legacy.*` before staging (it is never restored), stages `lib.sh`, `validate-runtime-env.sh` and `remote-rollback.sh` into a syntax-checked `rollback-driver.v.*` bundle stamped with `.driver-contract` = `strict-five-image-pins-v3`, and atomically repoints the `rollback-driver` symlink. A failed publication keeps the staged strict bundle for operator recovery. Install never prunes and never touches `rollback-driver.good`. After a successful activation, `promote_rollback_driver()` points `.good` at the activated bundle (strict bundles only) and prunes the rest. `remote-rollback.sh` resolves its directory with `pwd -P`, so one run never mixes bundle versions.
   - **Rollback driver behaviour:** the driver requires `.activated` for hardened targets. Before mutating any Docker tag or service, it refuses with exit `4` any broken pointer state (a directory `current_release`/`.activated`, or a non-symlink `current`), any target without a verified five-image manifest, or a target marked unsafe or confirmed missing pinned local images. It protects the outgoing active release's pins before retagging (aborting with retryable exit `1` before moving any runtime tag if an operational Docker error prevents retaining an available outgoing image), returns retryable exit `1` (rather than policy refusal `4`) on operational Docker retag/verify errors so `rollback-driver.good` can retry, never starts services from mutable tags, and never back-records pins. Once it starts changing services it stops Caddy first, reconciles PostgreSQL, runs `--provision-role-only` when applicable, reconciles API, frontends, and Caddy via `ensure_service_runs_image()`, runs smoke checks, and independently runs `verify_running_matches_manifest()` inside the driver before clearing `.rollback-unsafe` and publishing pointers with exact renames (`publish_line_file`). An EXIT trap keyed solely on the mutation flag (cleared only after full success), plus TERM/INT/HUP handlers, stops Caddy and the application services (preserving PostgreSQL) on any later failure or interruption. Post-mutation exits are never reported as `4`.
   - **Automatic recovery and observability:** on candidate failure after mutation, `remote-deploy.sh` recovers only when the pre-build tags were verifiably restored and the target's snapshot is complete, emitting explicit diagnostics naming the exact refusal cause(s) when recovery is unavailable. It always uses the shared driver, never the target release's own script. If the candidate driver is missing, non-strict, or fails for a non-policy reason, the deploy retries once with a strict `rollback-driver.good`, after revalidating the target's five pins. Policy refusals (exit `4`) are final. A reported success is independently verified (`current_release` and every running image ID, runtime tag, and retention tag against the pins) before the deploy prints `DEPLOY_RESULT=automatic-rollback-completed forced_smoke_failure=<bool> restored=<sha>` and exits `3`. `rehearse-staging.sh` requires that exact proof, a strict `v3` shared driver, distinct SHAs, and post-transition `verify_running_matches_manifest()` checks. Preflight prints Docker Engine, Compose, Buildx, storage driver, and `classic|containerd` image-store mode, and deploy/rollback emit UTC-timestamped operational and failure diagnostics to stderr without printing secrets.
   - **Interruption and broken sessions:** `remote-deploy.sh` keeps an equivalent EXIT trap for its own mutation window, open from the first service change until activation or verified recovery; neither `0` nor `3` can be reported from an open window. All fail-closed stops go through `failclosed_stop_app_services()`, which writes Compose output to `shared/deployment-state/failclosed.log`, so a cancelled CI runner (closed SSH pipes) cannot make the stop die of SIGPIPE. Cleanup ignores further TERM/INT/HUP/PIPE. SIGKILL, the OOM killer and power loss inherently bypass traps; the runbook requires re-running the driver for `current_release` afterwards.
   - **Recovery path for unpinned SHAs:** the pipeline only deploys branch tips and rejects stale SHAs, so the supported recovery for an unpinned or unsafe target is shipping the desired code as a new commit (for example a `git revert`).

## Rationale and Alternatives Considered

- **Immediate removal vs. staged `internalNumber: null` (H-01):** Dropping the JSON key immediately breaks polling on open `tmmin-web` tabs during single-host deploy where `api` updates before `tmmin-web`. Emitting `null` closes the privacy leak immediately while maintaining zero-error forward rollout.
- **Hard-requiring `POSTGRES_APP_PASSWORD` vs. staged zero-touch (H-07):** Requiring a brand-new secret immediately would halt automated staging/production deploys until manual secret creation. One-way HMAC derivation keeps `POSTGRES_PASSWORD` completely absent from `api` containers immediately while preserving an effortless upgrade path to an independent secret.
- **Separate Compose provisioning service vs. unified `migrate` CLI (H-07):** Keeping provisioning inside `migrate` preserves the verified 7-service Compose contract and ensures grants are always reconciled atomically right after schema migrations.

## Consequences and Rollback Continuity

- **Database schema & migration recovery:** One purely additive, forward-only index migration (`20261126002800_outbox_realtime_poll_index` adding `OutboxEvent_occurredAt_id_idx` on `OutboxEvent("occurredAt", "id")`); zero table/column changes or destructive SQL. Plain `CREATE INDEX` acquires a `SHARE` lock on `OutboxEvent` (blocking writes briefly during the index build, sub-second at current table sizes). Once applied cleanly, code-only rollback to `db60208` runs with the index present. If a migration is interrupted mid-build and leaves an unfinished `_prisma_migrations` record (`finished_at IS NULL`), `/ready` fails closed (`503`) until resolved; `HealthController.ready()` counts only unresolved attempts (`rolled_back_at IS NULL` or lacking a subsequent successful `finished_at IS NOT NULL AND rolled_back_at IS NULL` row for the same `migration_name`), so this release recovers cleanly to `200` after `prisma migrate resolve --rolled-back` followed by a successful `migrate` retry. Note that legacy `db60208`'s older `/ready` query still treats any historical `rolled_back_at IS NOT NULL` row as unfinished, so an emergency rollback to `db60208` after a `--rolled-back` recovery would require remaining on a release with the updated `/ready` predicate or removing the historical rolled-back row first.
- **Emergency rollback:** Legacy `POSTGRES_USER` and `POSTGRES_PASSWORD` remain intact on PostgreSQL, so rolling back to `db60208` remains possible as an emergency availability fallback — but only through the shared hardened driver (`shared/deployment-state/rollback-driver/remote-rollback.sh`) and only if `db60208` received backfilled `.activated-images` pins, which happens when it is `current` during the first hardened deploy and its five running containers pass the ownership/provenance checks; otherwise it is marked `.rollback-unsafe` and the supported recovery is shipping the desired code as a new commit through the pipeline (noting that rolling back to `db60208` temporarily resumes superuser API access and pre-fix behavior until a hardened rollback target is established), and open PR `tmmin-web` tabs continue functioning against a rolled-back `main` API by scrubbing legacy string `internalNumber` values to `null` at the client boundary. Once two hardened releases exist, rollback between hardened releases keeps least-privilege isolation intact via `--provision-role-only` (with fail-closed `REVOKE ALL` for any unknown forward-migrated immutable tables) provided `POSTGRES_APP_PASSWORD` is not rotated in-place mid-rollback window.
- **Zero-downtime runtime credential rotation choreography (H-07):** Because `migrate` executes `ALTER ROLE` on `POSTGRES_APP_USER` before `api` is recreated, adopting an independent `POSTGRES_APP_PASSWORD` secret (replacing the staged HMAC-derived password) or rotating it on live traffic should either use a brief maintenance window or a staggered dual-role switchover: (1) set `POSTGRES_APP_USER` to a new role name (e.g. `supplier_henkaten_app_v2`) alongside the independent `POSTGRES_APP_PASSWORD` and deploy (the old `api` stays authenticated on the prior role until replaced), then (2) drop the retired role once no rollback snapshot references it.
- **Single-instance deploy window:** Container replacement still incurs the existing brief reconnect window during `api` swap; SSE client backoff ensures unattended displays reconnect automatically.
- **Deferred work:** Staging/production SSH key & secret separation and production manual approval gates (H-08) remain explicitly deferred for dedicated ops/governance execution.

## Validation Plan

## Risks and Follow-up Work

- **Production pre-merge gate:** the read-only checks in `.agent/deploymentGuide.md` §9.5 (legacy container provenance and `OutboxEvent` size) must be run on the production VM before this change reaches `main`, because merging triggers the production deployment.
- **Late-commit realtime window:** `RealtimeEventPump` tolerates late commits within a bounded 10-second lookback. Outbox rows written by transactions that stay open longer (several commands allow 60–300 seconds) can miss live delivery until the next resync; a post-commit resync or commit-order cursor is tracked as follow-up.
- **Database-level privileges:** runtime role reconciliation revokes schema-level `CREATE` only. Revoking and verifying database-level `CREATE`/`TEMPORARY` for `POSTGRES_APP_USER` is tracked as follow-up.
- **Grant granularity:** non-immutable tables without a delete path still receive table-wide `UPDATE`/`DELETE`. Tightening to an explicit per-table DML matrix is tracked as follow-up.
- **Outbox retention:** `OutboxEvent` has no retention job, so index builds and replay scans grow with table size. Retention or archival is tracked as follow-up.
